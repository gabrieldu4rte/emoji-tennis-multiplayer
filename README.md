# Emoji Tennis Online

A real-time, two-player Pong-style tennis game in which players control avatars represented by emojis. A match takes place between two players connected simultaneously over the network, with state synchronized via WebSocket.

## Overview

The project consists of a Node.js server responsible for matchmaking players and running the authoritative match simulation, and a web client that holds all rendering logic, local ball prediction, and UI. There is no data persistence: matches, rooms, and scores exist only for the duration of the players' connections.

## Features

- Automatic matchmaking of two players into a game room.
- Character selection among twelve characters, each with its own pixel-art sprite (the emoji is still the identifier sent over the network).
- Fully procedural pixel-art assets: animated characters (idle, blink, run, swing, celebrate), rotating ball, four stadium arenas (grass, clay, hard court and a neon night court), animated crowd, bitmap font, logo and UI — all generated by code, no external image files.
- Visual effects: hit sparks and impact rings, racket swoosh, wall dust, fire trail on fast balls, screen shake, point banners, confetti, camera flashes in the stands, drifting cloud shadows and stadium lights.
- Chiptune sound effects and a looping soundtrack, also synthesized by code, with a mute toggle.
- Attract mode: two bots play an exhibition match behind the menu.
- A short 3-2-1 countdown before the first serve and a brief pause after each point.
- Touch/drag control on mobile and automatic scaling to the screen size.
- Keyboard-driven paddle movement, synchronized in real time between the two clients.
- Collision physics with ball angle and speed varying according to where it hits the paddle.
- Sound effects played via the Web Audio API, synchronized between both players.
- Scoring with a five-point limit and a victory screen at the end of the match, decided and confirmed by the server for both players.
- A custom visual theme, including animations for the waiting screen, scoreboard, and match end.
- Automatic reconnection in case of a dropped connection during a match, with a notice to the opponent and a grace period before the room is closed.
- Server-side validation of events received from clients, including paddle position, ball position, score, and sound effects.

## Technologies used

- Node.js
- Express, for the HTTP server and to serve the client's static files.
- Socket.IO, for real-time communication between server and clients.
- HTML5 Canvas, for rendering the game graphics in the browser.
- Web Audio API, for playing sound effects and music.
- A dependency-free Node.js asset generator (custom PNG and WAV encoders) for all sprites, arenas and audio.

## Requirements

- Node.js installed (the latest LTS version is recommended).
- npm, bundled with Node.js.

## Installation

Clone the repository and install the dependencies:

```
npm install
```

## Running the project

To start the server:

```
npm start
```

By default, the server starts on port 3000. The port can be changed via the `PORT` environment variable.

## Regenerating the assets

All images and sounds in `public/assets/` are produced by `tools/generate-assets.js`, which has no dependencies. The generated files are committed, so deployment (e.g. on Render) only needs `npm install` and `npm start`. After changing the generator, run:

```
npm run assets
```

## Opening the game

Once the server is running, open `http://localhost:3000` in the browser. To play a match, the address needs to be opened in two separate tabs, windows, or devices, simulating the two players.

## How to play

1. On the home screen, choose a character among the available emojis.
2. Click "Search Match" to enter the matchmaking queue.
3. Once a second player connects, the match starts automatically.
4. Control your character using the W and S keys, the up and down arrow keys, or by dragging on the court on touch screens.
5. The first player to reach five points wins the match.

## Architecture and internal workings

The server is the authority over the match. Its responsibilities are:

- Pairing the next connecting player with the player already waiting, creating a room identified by the combination of the two players' socket identifiers. Matchmaking is sequential (only one player waits to be paired at a time), but this does not limit the number of simultaneous rooms: each formed pair spawns an independent room, and new pairs keep being matched normally while earlier matches are still in progress.
- Simulating the ball at a fixed 60 steps per second for every room, using the same `physics.js` module as the client, and deciding hits, points, serves and the winner. Both players are therefore treated equally, regardless of who joined first.
- Broadcasting state snapshots (ball position and velocity, score, serve time and hit counter, stamped with the simulation time) whenever a hit or point happens, and at least every 100 ms otherwise.
- Validating player input: the server checks that the sender belongs to the room and to the role it claims, clamps paddle positions to the court and restricts the chosen emoji to the allowed list.
- Handling disconnections: when a player's connection is lost, the match is paused, the opponent is notified and the room is kept for a grace period (20 seconds). If the player reconnects, the ball is served again after a countdown. If a player leaves voluntarily through the menu, the room is closed immediately.

Network latency is handled on both ends:

- Each client estimates the server clock with periodic ping exchanges and renders the ball at the current server time: from each snapshot it simulates the ball forward locally, including wall bounces and paddle hits, so the ball moves smoothly between snapshots. When a snapshot disagrees with the local prediction, the difference is blended out over a few frames instead of teleporting the ball.
- Each client moves its own paddle locally and sends its position every frame, stamped with the estimated server time. When the ball reaches a paddle, the server looks up where that player's paddle was at that moment, waiting up to 200 ms for the input to arrive. A hit is decided by what the player saw on their own screen, within that limit.
- The countdown before each serve is scheduled from the serve time sent by the server, so both players see it at the same moment.
- The arena is chosen deterministically from the room identifier, so both players see the same stadium without any extra network traffic.

## Known limitations

- Automatic reconnection only covers dropped connections during an ongoing match, within the same browser tab; if the page is reloaded or closed, the match state is lost and cannot be resumed.
- Latency compensation trusts the timestamp of each paddle position within a 200 ms window, so a modified client could reposition its paddle slightly in the past. Players with more than 200 ms of latency get no further compensation and may see the ball pass through their paddle.
- Player and room state is kept in memory only, and is lost on every server restart.
